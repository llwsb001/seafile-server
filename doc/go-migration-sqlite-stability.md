## 任务 1｜排查探针

在隔离的原生 Linux 实例上，用同一 C 二进制、样本、负载参数、外部组件、CPU 和磁盘环境做对照。每次从独立的同一快照副本启动，按交替顺序运行各组，每组至少三次。优先缩短到能观察到锁冲突与虚拟库收敛关系的负载片段，再用完整负载确认修正效果。保留全部尝试，包括中断和超时。

| 组别 | 观测方式 | 比较目的 |
| --- | --- | --- |
| A | 保留当前 `F_GETLK`、RSS 采样和在线断言。 | 重现已知失败并确定最早出现差异的操作。 |
| B | 关闭周期采样，保留负载及在线断言。 | 对照 A，检查周期采样与失败是否相关。 |
| C | 沿用 B，把验收工具直接查询 SQLite 的断言移到停写后或停服后，在同一数据副本上执行。 | 对照 B，检查 head、统计和虚拟库投影查询的影响。保留客户端真实读写和权限检查。 |

A、B、C 三组使用同一份写入时间表。预先固定各次客户端操作的顺序和相对发起时点。B 组在线查询只记录结果，发起下一次写入仍按时间表。B/C 保持轮询 RPC 的频率和时间窗口一致，只改变直接 SQLite 断言的执行时点。记录计划与实际发起时点，保留偏离时间表的尝试，并注明这些尝试能支持哪些结论。等在途请求结束后，在本轮数据副本上执行持久状态断言。延后查询的组只比较失败和最终状态，报告注明观测时间点。

Go 另做配对对照。使用同一归档、快照和写入时间表，交替运行开启与关闭 `GoFileWriteQueue` 周期查询两组，每组至少三次。两组使用相同的 RSS、`F_GETLK` 采样和业务断言，关闭组的采样线程不为队列打开 SQLite 连接。两组都核对收敛、写入结果和停服后的队列状态。记录写入失败、收敛和排空耗时，据此选择正式 Go 验收的采样方式。

- 列出采样和断言的数据库连接、文件描述符、访问频率和持续时间。定位 `monitor`、`virtual_write`、`head`、`verify_stats` 和 `virtual_projections`。
- 用独立进程持有已知 SQLite 写锁，分别验证回滚日志和 WAL 下探针能发现其所检查的锁，释放后读数恢复。记录 SQLite 日志模式。报告区分 `F_GETLK` 观测到的文件锁、实际 RPC/HTTP 失败，以及服务端打印的 SQLite 错误。
- 对齐负载操作、锁采样、`COMMIT` 或 `UPDATE VirtualRepo` 日志以及各次读写确认的时间。保存库 ID、最后确认写入、两边 head、`VirtualRepo.base_commit`、文件摘要和退出状态。若观测方式影响失败率，保留调整前后的复现。
- 修正探针后，验证停写或停服检查仍能检出缺文件、错误 head、陈旧统计或未收敛的虚拟库。按历史入口复跑受影响的 v8/v9 用例。C 在关闭采样和延后查询后仍失败时，报告复现条件、频率及停止点，继续使用同一冻结的 C 版本。

## 任务 2–3｜Go 独立持续负载

使用同一 SHA-256 的 Linux SQLite 归档完成安装、持续负载和 v9 回退。校验归档与安装目录内的 `SHA256SUMS`，通过 `seafile-sqlite` 启动，核对 controller、核心、fileserver 及通知进程的实际可执行文件。使用锁定的 Seahub、真实通知服务和两个桌面客户端，复用现有负载中的文件和操作。 [归档与安装说明](../release/sqlite/README.md)

Go 独立运行入口由任务 2 实现，接收归档、摘要、安装目录、负载依赖与报告路径。现有 `baseline` 和 `compare` 入口继续用于 C 基线及相对性能。

| 验收项 | 通过条件 |
| --- | --- |
| 运行时长 | 原生 Linux amd64 上完成三轮。每轮从独立数据副本启动，完成一轮预热后持续至少 180 秒，测量窗口内至少完成两次完整负载。报告记录架构、环境配额、实际时长及循环数。 |
| Web、客户端与权限 | 经真实 Seahub 上传、下载 24 MiB 文件并核对 SHA-256，删除后路径消失。两个真实客户端每轮负载循环合计写入 64 个 4 KiB 文件，双端同步树与预期一致。无权限用户和无效令牌均被拒绝，所有已确认写入在最终状态可核对。 |
| 虚拟库与统计 | 每次虚拟库写入在现有 60 秒时限内收敛。视图与原库路径内容一致，base commit 的投影与当前视图对应，相关队列为空。文件数与字节数对应当前 head。 |
| 排空与重启 | 关闭测试写入并等在途请求完成。Go 队列在现有 60 秒时限内归零。停服后核对 `PRAGMA integrity_check`、head、对象引用和文件摘要。同一数据重新启动 Go，已确认的写入仍可读并能继续增量同步。 |
| 失败与诊断 | 数据不一致、核心或子进程意外退出、写入失败、收敛或排空超时均使该轮失败。记录 SQLite 错误、首个失败操作、负载时序和剩余队列。Web 与同步延迟 p50/p95、吞吐、RSS 峰值、文件锁观测、队列峰值及排空耗时随原始报告保存。 |

本阶段用数据正确性和有界收敛签收 Go 独立负载。性能数据保留原始值和分位数，供以后比较。冒烟仅用于检查环境和入口。缺少完整轮次、有效样本或归档摘要不符时，运行器返回非零。
